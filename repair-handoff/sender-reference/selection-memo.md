# R045 发件端备查：两种三格位取法与伴音取舍

## 实际源材料

- 母带：`sender-reference/source/repair-freeze-lab-r045.mkv`
- SHA-256：`c2ad1b308a9c60778dd8b9bf145782cf6ce4096eb682f663c0c002416881b900`
- 扫描原件：`sender-reference/source/scan.json`
- 全部源格 PNG 与地址：`sender-reference/frame-ledger/`
- 整段源 WAV：`sender-reference/source/full-source-8k-mono.wav`
- 可发 ZIP：`outgoing/repair-desk-R045.zip`
- ZIP SHA-256：`29c027503d5694f898c4035d0990220af2421827d1253c9370418e4aa6637f33`

无图段为 `5000000..6000000` μs。洞前、洞后都保留了多个可取源格；
完整台账共有 17 个源格。

## 必须保留的三个“陷阱”事实

1. **同一长格跨多个目标点**：`V08-03500ms` @ `3500000..4500000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰。目标
   `T-L1@3700000, T-L2@4200000`
   都映射到这一个源格。
2. **洞两侧同像素但不是同一源格**：
   - 洞前：`V09-04500ms` @ `4500000..5000000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰
   - 洞后：`V10-06000ms` @ `6000000..6500000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰
   - 两者 raw gray SHA-256 相同：`True`；
     源格 ID 相同：`False`（应为否）。
3. **两种零声不能混写**：主 WAV 的 `SIL-REC` 是 muxed PCM 全零、源覆盖内的实录零声；
   `FILL-INNER` / `FILL-LATER` 是源无覆盖、摘片器填零。地址清单给了绝对采样区间。

## 首选发件取法（已封入 outgoing ZIP）

三个格位：

1. 长格证据：`V08-03500ms` @ `3500000..4500000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰
2. 洞前边界：`V09-04500ms` @ `4500000..5000000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰
3. 洞后边界：`V10-06000ms` @ `6000000..6500000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰

这段组合在三个格位内同时完成两件事：

- 给收件方一个“两个目标地址确实可落到同一源格”的正例，避免把地址清单中的同格映射误读成缺图；
- 保留无图段两侧的精确边界格，用相同像素测试“看似连续”，再用不同源地址和覆盖洞否定“同一格跨洞”。

伴音首选 `audio/R045-primary-mono.wav`：`4400000..7600000` μs。
它同时包含洞前/洞后强标记、实录零声、源内低鸣、两个摘片补零段和补零后恢复音。
当返修棚可能继续争论“零声是不是源里的”“后面的断音是否同源”时，优先发这段较宽 WAV。

## 另一种同样满足三格位限制的取法

目录：`sender-reference/alternative-selection/`

1. 洞前边界：`V09-04500ms` @ `4500000..5000000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰
2. 洞后边界：`V10-06000ms` @ `6000000..6500000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `0/0`‰
3. 冻帧起点附近见证格：`V07-03000ms` @ `3000000..3500000` μs, raw SHA `1fc29f1fb8e03924…`, 与前格差异 `54865/14695`‰

它仍保留判断无图段所需的两侧边界和地址清单，因此足以判断“同像素但两个源格、中间有洞”。
它把首选方案中的“长格正例”换成更早的第三源格；适合以下情况：

- 收件方不再争论目标点为何映射同一格，而争论洞前冻帧是否只是最后一帧的偶发/解码残影；
- 需要证明静止图案在边界之前已持续一段，而不是只靠最后一个边界格；
- 首选长格格位的地址映射已由发件端台账确认，且本次返修只要求判定跨洞事实。

如果争论点变成“洞后第一格是否为孤立解码重复格”，还可以把第三格换成洞后第二格
`V11-06500ms`（`6500000..7000000` μs，
raw SHA `1fc29f1fb8e03924…`）。该候选已在完整台账中，
但不要在未重新生成三格位包时直接加塞成第四格。

## 伴音何时换另一段

备选 WAV：`audio/R045-alt-boundary-mono.wav`，地址窗
`4500000..6250000` μs。它更短，仍包含：

- 洞前标记 `L-BEFORE` 与实录零声 `SIL-REC`；
- 无图段内源内低鸣和一个明确的摘片补零段 `FILL-INNER`；
- 洞后标记 `R-AFTER`。

当返修单只关心洞两侧是否有源伴音、表单/邮件对附件时长或大小敏感，或较宽 WAV 中
第二个补零段会让收件人把“后段声洞”与本次画格洞混淆时，优先使用这段紧边界 WAV。
若对方要求一并判断后段声音覆盖、补零后恢复或需要额外 RMS 校准材料，则应保留首选宽 WAV。

## 复跑

```sh
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python repair-handoff/build_repair_handoff.py
```

本工作区实际构建时若使用系统 Python 3.11，可用 ABI 兼容的 PyAV 18.x：

```sh
PYTHONPATH=/tmp/slatewatch-pydeps:/workspace \
  python3 repair-handoff/build_repair_handoff.py
```

复跑会重建 `outgoing/` 与 `sender-reference/`。媒体内容由固定时码、采样函数和种子生成；
ZIP 时间戳已固定，但容器字节/ID 若由不同 FFmpeg/PyAV 版本写出可能变化，应以当次
`addresses.json` 中的 SHA-256 为准。
