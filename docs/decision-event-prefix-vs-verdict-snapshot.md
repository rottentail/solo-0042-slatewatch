# 决策记录：冻结包保留完整事件前缀，而非仅裁决快照

- 日期：2026-11-24
- 范围：`slatewatch` 冻结包（`seal.py` / `service.py` / `store.py`）中 `review.json` 应保存什么材料，使接收方能核对一个包基于哪条审片前缀
- 状态：**决定保留完整事件前缀**（当前仓库实现已是该方案，本记录确认并给出依据）
- 复现实验：`experiments/prefix_vs_snapshot_probe.py`（对真实 `reels.basalt` MKV 跑真实服务代码，非桩件）

## 1. 背景与两个候选

审片状态不是直接存储的，而是由不可变扫描事实与该扫描上的人工记录**投影**出来的
（`review.adjudicate`，`slatewatch/review.py:50`）。人工记录是只追加的事件流：
`review_events` 表带单调 `seq`，分 `intent`（制作意图）和 `ruling`（人工裁决）两类
（`slatewatch/store.py:29-36,73-86`）。裁决只看同一候选的**最后一条** ruling；
没有 accept/hold 裁决时，意图完全覆盖候选才判 `expected`，否则 `pending`。

冻结包的 `review.json` 有两种选材：

| 方案 | 包内材料 | 标识依据 |
| --- | --- | --- |
| A. 裁决快照 + 可检查标识 | 投影结果：每候选 `status`、`ruling`（仅最后一条）、汇总计数 | 对投影表面取哈希 |
| B. 完整事件前缀（选用） | 冻结时刻全部 `intents` 与 `rulings`（含 `seq`、被覆盖的旧裁决、理由、复核人），外加投影结果 | 对含前缀的整个目录取 SHA-256，即现有 `seal-…` ID |

当前实现是 B：`service.seal` 先 `adjudicate` 再把整个 review 投影（其中 `intents`、
`rulings` 即 `timeline()` 返回的完整前缀）写入 `review.json`（`slatewatch/service.py:90-98`，
`slatewatch/seal.py:17-40`）。

## 2. 真实样片上的对照实验

### 2.1 同一表面状态，两条不同事件历史（裁决路径）

同一 `basalt` 字节、同一登记描述与规则版 → 同一 `scan`/`hit` ID，分别进两个独立保管库：

- 历史 A：对右声道削顶候选依次 `accept → reset → hold`（3 条 ruling，最后一条生效）
- 历史 B：同一候选只登记 1 条 `hold`

实测（probe PAIR A）：

```
A/B 表面 counts 均为 {"pending":5,"expected":0,"accepted":0,"held":1}，rollup=hold
surface equal: True；snapshot id equal: True
A 前缀保留 [(1,accept),(2,reset),(3,hold)]；B 前缀只有 [(1,hold)]
prefix fingerprints 不同；seal ids 不同（seal-ad9d… vs seal-16cb…）
```

### 2.2 同一表面状态，两条不同事件历史（意图路径）

对左声道静音候选：

- 历史 C：1 条完整覆盖的意图 → `expected`
- 历史 D：先 1 条**不完整**覆盖的意图（候选仍 `pending`），再补 1 条完整覆盖的意图 → `expected`

实测（probe PAIR B）：最终表面逐候选状态、计数完全相同，快照标识相同；
但前缀里意图条数（1 vs 2）、`seq`、理由文本都不同，前缀指纹不同。

### 2.3 晚到的意图改变判读

对片头黑场与削顶候选先各登 `hold`，此时冻结出包 S1；随后制作方的黑场意图**晚到**：

1. 晚到意图到达瞬间：黑场候选上 `ruling` 仍是 `hold`，人工裁决优先，状态保持 `held`，
   但 `intent_sequences` 已记录 `[3]`。整体 rollup 与计数不变。
2. 复核人随后把黑场的 hold 撤回（`reset`）：同一候选改判 `expected`，
   `intent_sequences=[3]`——这个结论只能由晚到的意图解释。
3. 重新冻结得到 S2，seal ID 与 S1 不同；S1 仍可独立校验通过，其 `review.json` 中
   `intents` 数量为 0、黑场冻结在 `held`。
4. 用 S1 内嵌前缀对同一不可变扫描重放 `adjudicate`，**精确复现**冻结表面。
5. 模拟只拿裁决快照做复位重放（去掉意图前缀）：黑场复位后只能得到 `pending`，
   无法得到真实的 `expected`。
6. 纯快照标识在「晚到意图到达前后」**完全相同**（`snapshot-10a31e41…` 相等），
   即快照标识对这一事件不可感知；只有复位改变了表面后快照 ID 才变化。

## 3. 两种材料各能证明什么

### 完整事件前缀（方案 B，现实现）

包内 `review.json` 同时含完整 `intents`/`rulings`（带 `seq`）、投影状态与每候选的
`intent_sequences`；`scan.json` 是不可变扫描；`index.json` 对每个成员记录
SHA-256，整个 ZIP 另有内容地址，`seal.verify` 逐成员校验（`slatewatch/seal.py:43-65`）。
可证明：

1. **冻结时刻的完整裁决结论**及其全部依据：每条意图/裁决的时间顺序、理由、复核人、
   被撤回的旧裁决（如 accept→reset→hold 的改判链）。
2. **可独立重放**：接收方用包内 `scan.json` + 前缀重新跑同一套 `adjudicate` 规则，
   必须逐候选复现包内状态（实验 2.3 步骤 4 已验证）。规则与扫描均不可变，重放无歧义。
3. **前向血缘**：同一扫描后续再封包时，前缀是旧前缀的超集；对比两个包的前缀即可看出
   期间新增了哪些 `seq`（实验中 S1 前缀 0 意图 → S2 前缀含 seq=3 的晚到意图）。
4. seal ID 对前缀内容敏感：表面相同但历史不同的两个包得到不同 seal ID
   （2.1、2.2），接收方仅凭 ID 与 `index.json` 就能区分「怎么得出的结论」。

### 裁决快照 + 可检查标识（方案 A，假设替代）

可证明：冻结时刻**是什么结论**，以及该投影自身未被篡改（标识覆盖投影字节）。
不可证明：

1. 结论的产生路径——accept→reset→hold 与一次 hold 不可区分（2.1）；
   一次到位的意图与「先错后补」的两条意图不可区分（2.2）。理由、复核人、改判链全部丢失。
2. **无法离线重放复位**：撤掉最后一条裁决后，候选落回 `expected` 还是 `pending`
   取决于意图前缀；快照里没有意图，重放必然缺依据（2.3 步骤 5：得到 `pending` 而非
   真实的 `expected`）。
3. **对晚到事件无感知**：晚到意图不改变表面时，快照标识不变（2.3 步骤 6），
   接收方无法从包材料判断该意图在封包前是否已到达；一旦后续复位，旧包无法解释新判读。
4. 只能与在线保管库对账才能补全历史，离线交接退化为「信任出包方数据库」。

## 4. 离线核对与后续复位时的判断变化

| 场景 | 完整事件前缀（B） | 仅裁决快照（A） |
| --- | --- | --- |
| 离线校验包完整性 | 逐成员 SHA-256 + ZIP 内容地址，通过即全部材料可信 | 同样可校验，但可信范围仅投影本身 |
| 离线核对「基于哪条审片前缀」 | 直接读 `intents`/`rulings` 的 `seq` 与内容，并重放 `adjudicate` 复核 | 无法回答；只能看到最终 status |
| 区分同表面不同历史 | seal ID 与前缀指纹不同，可区分 | 快照 ID 相同，不可区分 |
| 复核人撤回裁决（reset）后的再判读 | 用包内前缀+扫描本地重放：有覆盖意图→`expected`，无→`pending`，结论可解释 | 缺意图前缀，重放结果可能与线上判读相反且无从察觉 |
| 晚到意图到达但表面未变 | 前向对比新旧包前缀即可发现新增 `seq`；旧包仍自洽冻结在旧状态 | 新旧包快照标识相同，事件被完全隐藏 |
| 与出包方数据库脱离 | 包即自洽证据，ZIP + Python 标准库即可复核 | 必须回连保管库查 `review_events` 表 |

## 5. 决定

**冻结包继续保存完整事件前缀（方案 B），不改为裁决快照。**

理由：接收方的核对需求不止于「结论是什么」，还包括「基于哪条审片前缀、能否在脱离
出包方数据库时重放与解释后续复位」。实验表明快照材料在同表面异历史、晚到意图、
离线复位三个场景下都丢失关键判别力，而前缀材料的额外成本仅是 `review.json` 中
只追加的小体积 JSON 事件（媒体证据体积不受影响），且现有 seal ID 与逐成员哈希机制
天然提供前缀级的可检查标识，无需新增机制。

### 配套约束（沿用现状，避免方案退化）

1. `review_events` 只追加、`seq` 单调；`reset` 也是追加事件而非删除（`review.OUTCOMES`），
   保证前缀不可改写。
2. 封包后续写的人工记录不得回写旧 ZIP；新结论必须新 seal ID（`service.seal` 每次现算
   `adjudicate` + 内容寻址，实验 2.3 已验证 S1/S2 ID 不同且 S1 仍校验通过）。
3. 扫描、规则版不可变并整体入包（`scan.json`），这是前缀可离线重放的前提，不得拆出。
4. 若未来确需轻量化分发，可在**另发**的衍生材料中提供快照，但快照标识必须同时引用
   其来源 seal ID，不得作为独立交接凭证。

### 复现方式

```sh
.venv/bin/python -I experiments/prefix_vs_snapshot_probe.py
```

脚本在临时目录生成真实 `basalt` MKV，经 `Slatewatch` 服务登记、扫描、追加意图/裁决、
封包，并实际解压 ZIP、调用 `seal.verify` 与 `review.adjudicate` 完成离线重放。
